## STEP 1 — 현재 구조 분석

### 1-1. 게임 루프의 실체

게임 전체가 **고정 길이 배열 하나**로 돌아갑니다.

```js
// 6-ui.js:11  [13] UI — 상태
const PHASES=['seasonStart','train','event','moment1','seg1','event','moment2','seg2',
              'train','teamEvent','moment3','seg3','rank','ksMoment','post','award','traits',
              'combo','nat','trade','fa','retire','leagueOff','yearEnd'];

// 6-ui.js:208
function advance(){
  if(G.ui&&G.ui.after){G.ui.after=0;G.pi--;}   // 결과 화면이면 같은 페이즈 재진입
  G.pi++;
  if(G.pi>=PHASES.length)G.pi=0;                // 24개 다 돌면 처음으로
  const r=runPhase(PHASES[G.pi]);
  if(r==='skip')return advance();               // 조건 미달이면 즉시 다음 페이즈
}
```

`G.pi`(phase index)가 유일한 시간 커서입니다. 한 바퀴 = 1시즌.
`runPhase()`는 24개 `case`의 스위치이고, 각 case는 `scene({...})`을 호출하거나 `'skip'`을 돌려줍니다.

**이 구조의 좋은 점**: 페이즈는 이미 "토큰 하나 = 화면 하나"로 정규화돼 있습니다.
v3.0은 이 스위치를 버리는 게 아니라, **배열을 고정값에서 캘린더 생성물로 바꾸면 됩니다.** (STEP 3-1)

### 1-2. 시간 표현이 실제로 어디에 있나

시간 정보는 세 군데에 흩어져 있고, **전부 문자열 라벨**입니다.

| 위치 | 코드 | 성격 |
|---|---|---|
| `p.year` | `6-ui.js:295` `p.age++;p.year++` | 유일한 실제 시간 상태 |
| `SEGS` | `6-ui.js:14` `{seg1:'4~5월',frac:.34}` | 3구간 × 경기 비중 |
| `when` 라벨 | `scene({when:'${p.year}년 7월 · 올스타 휴식기'})` | 화면에 찍는 문자열. 로직 아님 |

즉 **"월"이라는 개념은 표시용 문자열로만 존재하고, 상태로는 없습니다.** 새로 만들어야 합니다.

### 1-3. 시즌 시뮬레이션은 이미 비율 기반

가장 중요한 발견입니다.


### 1-4. 부상 판정은 호출 횟수에 민감 (밸런스 리스크)

```js
// 5-player.js:250
function rollInjury(p,full){
  let c=.055*full*(1+(p.fatigue-40)/110)*...;
  if(!R.c(clamp(c,.01,.6)))return null;   // ← 호출당 주사위 1번
  ...
}
```

`full`에 비례하지만 **판정은 호출당 1회**입니다.
- 현재: 3회 × 확률 c → 무부상 확률 `(1-c)³`
- v3.0: 6회 × 확률 c/2 → 무부상 확률 `(1-c/2)⁶`

기댓값(연간 부상 횟수)은 같지만 분포가 달라집니다. 특히 `clamp(c,.01,.6)`의 상한에 걸리는 고피로 구간에서 v3.0이 **부상이 더 자주 납니다**. Phase 5에서 반드시 재측정하고 `.055` 계수를 조정해야 합니다. (현재 기준값: 커리어당 부상 2.3회)

## STEP 3 — v3.0 아키텍처

### 3-1. 캘린더 큐 — 핵심 변경 하나

`PHASES` 고정 배열을 **월이 생성하는 페이즈 큐**로 바꿉니다. `runPhase()`의 24개 case는 **그대로 둡니다.**

```js
/* 7-calendar.js (신규) */
G.cal = { year:2026, month:1, queue:[] };

// 월 → 페이즈 토큰 배열. 기존 페이즈 이름을 그대로 재사용한다.
function buildMonth(m){
  const p=G.p;
  switch(m){
  case 1:  return ['monthStart','action'];                          // 비시즌
  case 2:  return ['monthStart','action','event'];                  // 스프링캠프
  case 3:  return ['monthStart','action','rosterSet'];              // 개막 엔트리 발표
  case 4: case 5: case 6:
  case 7: case 8: case 9:
           return ['monthStart','action','games','moment','levelCheck'];
  case 10: return ['monthStart','rank','ksMoment','post'];
  case 11: return ['award','traits','combo','nat'];                 // 시즌 결산
  case 12: return ['monthStart','action','trade','fa','retire','leagueOff','yearEnd'];
  }
}

function advance(){
  if(G.ui&&G.ui.after){G.ui.after=0;G.cal.queue.unshift(G.cal.last);}
  if(!G.cal.queue.length){                 // 이번 달 끝 → 다음 달
    G.cal.month++;
    if(G.cal.month>12){G.cal.month=1;}
    G.cal.queue=buildMonth(G.cal.month);
  }
  const ph=G.cal.queue.shift(); G.cal.last=ph;
  if(runPhase(ph)==='skip')return advance();
}
```

**이 설계의 의미**
- `runPhase()`의 기존 case(`event` `moment1` `rank` `post` `award` `traits` `combo` `nat` `trade` `fa` `retire` `leagueOff` `yearEnd`)가 전부 살아남습니다. 이름만 재배치.
- 새로 추가되는 case는 `monthStart` `action` `games` `rosterSet` `levelCheck` 5개뿐입니다.
- **주간 확장이 공짜입니다.** `buildMonth()`가 `['action']` 대신 `['action','action','action','action']`을 돌려주면 그대로 주간 4칸이 됩니다. UI만 4칸으로 그리면 끝.

### 3-4. 플레이어를 리그에 편입 (요구 11·12)

**가장 구조적인 변경입니다.** 플레이어의 그림자 엔트리를 `L.players`에 넣습니다.

```js
/* 4-league.js 확장 */
function syncPlayerEntry(p){
  let e=L.players.find(a=>a.isPlayer);
  if(!e){ e={id:'ME',isPlayer:true}; L.players.push(e); }
  Object.assign(e,{ name:p.name, pos:p.pos, age:p.age, team:p.team,
                    ovr:ovr(p), pot:p.pot, retired:p.retired, lv:p.lv, role:p.role });
  return e;
}
```

그러면 기존 `assignRoles()`가 **수정 없이** 플레이어를 팀 내 정원 경쟁에 포함시킵니다.
`decideLevel()`은 절대 기준 계산에서 **그림자 엔트리 조회**로 바뀝니다.

```js
function levelCheck(p){
  const before=p.lv;
  syncPlayerEntry(p); assignRoles();
  const e=L.players.find(a=>a.isPlayer);
  p.lv = e.lv==='2군' ? '2군' : e.role;     // '주전'|'백업'|'선발'|'불펜'|'2군'
  if(before==='2군' && p.lv!=='2군') return firstCallUp(p) || callUpScene(p);
  if(before!=='2군' && p.lv==='2군') return demotionScene(p);
  return 'skip';
}
```

효과:
- 우리 팀 포수 depth에 나보다 나은 선수가 있으면 **종합 65여도 2군**입니다
- 트레이드로 팀을 옮기면 출전 기회가 실제로 바뀝니다 (구단 성향과 연결)
- 매월 판정하므로 **시즌 중 콜업/강등**이 자연스럽게 사건이 됩니다
- `teamRating()`에 플레이어가 포함돼 내 성적이 팀 순위에 반영됩니다

**첫 콜업(요구 12)** 은 `p.flags`에 `firstCallUp`이 없을 때만 뜨는 전용 연출 + `p.timeline.push({y,m,t:'프로 1군 데뷔'})`.

### 그림자 엔트리는 AI 루프에서 전부 걸러야 했다

이게 이번 작업에서 제일 조심스러웠던 부분입니다. `L.players`를 도는 AI 전용 루프가 플레이어를 AI로 착각하면 조용히 망가집니다. 실제로 걸러낸 곳:

| 위치 | 안 걸렀으면 |
|---|---|
| `aiDevelop` | **한 해에 두 번 나이를 먹는다** (yearEnd + 오프시즌) |
| `aiRetire` | 플레이어가 AI 기준으로 은퇴 처리된다 |
| FA 이동 | 모르는 팀으로 순간이동한다 |
| 트레이드 | 같은 증상 + `a.teams` 없어서 크래시 |
| 정원 관리 방출 | **선수가 조용히 사라진다** |
| `aiSeasonAll` | 시즌이 두 번 시뮬레이션된다 |
| `leagueAwards` | 시상 후보에 내가 두 번 올라간다 |
| `teamRating` | 내 기여가 ovr + WAR로 이중 계산된다 |
| 우승팀 `aw.champ++` | `a.aw` 없어서 크래시 |
| `lines.slice` | `a.lines` 없어서 크래시 |

10곳 전부 `isAi()` 가드를 붙였고, 크래시 3건은 실제로 테스트에서 터져서 잡았습니다.

### 능력치만으로 자리가 정해지지 않는다

순수 ovr로만 경쟁시키니 첫 콜업 중앙값이 **24~28세**로 나왔습니다. 2군에서 5년 넘게 썩는 게 기본값이 되어버려서, 출전 기회 보정을 넣었습니다.

```js
function opportunity(p){
  v += (CUL(p.team).youth-3)*1.5;              // 육성 구단이면 기회가 빨리 온다
  v -= (CUL(p.team).vet-3)*0.8;                // 베테랑 선호면 신인은 밀린다
  if(p.age<=23) v += (p.pot-ovr(p))*.17;       // 어리고 잠재력 있으면 경험을 쌓게 한다
  if(p.age>=32) v -= (p.age-31)*1.1;           // 나이가 들면 자리가 좁아진다
  v += (p.rel.manager-50)*.06;                 // 감독의 신뢰
  if(p.draftRound<=2) v += 1.6;                // 상위 지명은 기회를 더 받는다
  if(p.flags.includes('demoted')) v -= 1.0;    // 한 번 내려간 선수는 눈도장이 찍힌다
}
e.ovr = ovr(p) + farmPush(p) + opportunity(p);
```

이걸로 요구 18(구단 성향이 실제 게임플레이에 영향)이 수치로 연결됐습니다. 육성 구단에 지명되면 2군 탈출이 빠르고, 감독에게 잘 보이면 기회가 옵니다.

`farmPush(p)`는 2군 성적을 ±6 범위로 환산합니다 — **2군에서 3할 치면 실제로 콜업이 당겨집니다.**

### 2군 성적은 따로 쌓는다

`simHalf`가 `p.lv==='2군'`이면 `p.farm`에 기록합니다. 통산 기록(`p.tot`)에는 들어가지 않습니다 — KBO 통산 기록이 1군만 집계하는 것과 같습니다. 성장(`expGrowth`)은 그대로 일어나므로 2군은 "기록은 안 남지만 크는 시간"이 됩니다. 커리어 표에는 `2군` 등급으로 별도 표시됩니다.

### 먼저 고친 것 — 포지션 불일치

투수에게 **"네 스윙, 지금 폼으로는 안 통해"** 가 뜨고 있었습니다. 원인이 두 가지였습니다.

1. `storyEvent()` / `teamEvent()` 에 **포지션 필터가 아예 없었습니다.** `MOMENTS`만 `pos`로 걸러지고 있었습니다.


같은 이벤트가 이렇게 갈라집니다.

| | 타자 | 투수 |
|---|---|---|
| 감독의 지시 | "네 **스윙**, 지금 상태로는 안 통해" | "네 **투구폼**, 지금 상태로는 안 통해" |

| 몸의 신호 | **손목**이 무겁다 | **어깨**가 무겁다 |

함께 고친 구조적 버그:

- **`E_COACH_RETURN` 모순** — "새 타격코치가 부임했다"인데 투수면 `control`·`stuff`를 올리고 있었습니다. 타격코치가 제구를 가르치고 있었던 겁니다. `applyResult`에 `stKey:[주능력,부능력]`을 추가해 포지션에 맞는 능력치가 오르게 했습니다.

- **`M_DEBUT`** — `pos:'all'`인데 실패 문구가 "초구에 헛스윙"이었습니다. 투수에겐 "초구가 크게 빠졌다"로 갈라집니다.
- **`TE_INCHEON_1`** — "투수 왕국인데 야수 시설은 뒷전"이 투수에게도 떴습니다. 투수용(`pos:'pitcher'`, 추적 장비)과 야수용 둘로 쪼갰습니다.

## 3-16. 주간 시스템 (요구 4 최종 목표)

### 시즌중만 4주로 쪼갠다

Phase 1에서 예고한 대로 `buildMonth()` 한 함수만 바꾸면 됐습니다.

```js
function seasonMonth(tail){
  const q=['monthStart'];
  for(let w=1;w<=4;w++) q.push('week'+w,'action','games');   // 주마다 행동 1회 + 그 주 경기
  return q.concat(tail||[]);
}
case 4: return seasonMonth(['moment']);
case 5: return seasonMonth(['event','levelCheck']);
```

연 턴 수는 **시즌중 6개월×4주(24) + 비시즌 6개월(6) = 30턴**입니다. 전체 주간(48턴)은 비시즌에 할 일이 없어 반복감이 생기므로 시즌중만 쪼갰습니다. `games`는 `weekFrac() = 월 frac ÷ 4`로 그 주 몫만 시뮬레이션하므로, 시즌 총량은 여전히 정확히 1.00입니다.

### 호출 횟수가 4배가 되며 깨진 것 4건

월간에서 잘 맞던 수치가 주간에서 전부 틀어졌습니다. 원인이 제각각이라 하나씩 잡았습니다.

## 3-17. 모바일 최적화 (요구 32)

### 저장이 실제로는 되지 않고 있었다

가장 큰 발견입니다. `Store`가 `window.storage`라는 **비표준 API**만 보고 있었습니다.

```js
// 기존 — 브라우저에는 window.storage 가 없다 → 항상 예외 → 메모리로 폴백
async get(k){ try{ ... window.storage.get(k) ... }catch(e){ return MEM[k]??null; } }
```

즉 **새로고침하면 세이브가 사라졌습니다.** 데스크톱에서는 눈치채기 어렵지만, 모바일은 앱 전환만으로 탭이 메모리에서 내려가므로 치명적입니다. `window.storage → localStorage → 메모리` 3단 폴백으로 바꾸고, 용량 초과 시 오래된 키를 비우고 재시도하게 했습니다.

검증: 새로고침 후 `{2026년 9월 3주차, 저장, 18세}` 그대로 복원됩니다.

### 화면마다 270KB를 직렬화하고 있었다

`scene()`이 매번 `save()`를 호출했습니다. 세이브에는 리그 전체(AI 300명)가 들어 있어 약 270KB입니다. 주간 전환으로 화면이 3배가 되면서 모바일에서 체감되는 렉이 됩니다.

400ms 디바운스로 합치고, **탭이 숨겨지는 순간(`visibilitychange`/`pagehide`)에는 반드시 기록**하게 했습니다. 큐 전체를 저장하므로 마지막 한 번만 기록돼도 정확히 이어집니다.

### 상태창 접기

인생 보드가 세로 285px을 차지해 390×844 화면에서 선택지가 아래로 밀렸습니다. 우상단 버튼으로 게이지·최근사건을 접으면 **99px**로 줄고, 접힘 상태는 저장됩니다.

| 기기 | 보드 | 첫 선택지 y | 접은 뒤 |
|---|---|---|---|
| iPhone SE 375×667 | 285px | 427 | 99px / y=241 (186px 확보) |
| iPhone 14 390×844 | 285px | 427 | 99px / y=240 |
| Pixel 7 412×915 | 298px | 449 | 99px / y=250 |
| 가로 844×390 | 100px* | 232 | — |

\* 가로 모드는 세로가 짧으면 자동으로 접힙니다(`max-height:500px and orientation:landscape`).

### 그 밖에

- **홈화면 추가(PWA)** — `manifest.webmanifest` + iOS 메타 + 512px 아이콘. 홈화면에서 주소창 없이 전체화면으로 실행되고, `overscroll-behavior:contain`으로 당겨서 새로고침이 막힙니다.
- **터치 타겟** — 44px 미만 버튼 0개. `touch-action:manipulation`으로 더블탭 확대 방지, `:active` 피드백.
- **스크롤 복귀** — 씬이 바뀔 때 본문이 화면 위로 벗어나 있으면 첫 줄로 되돌립니다. 긴 선택지를 읽고 내려간 상태에서 다음 장면을 놓치지 않습니다.
- **≤400px 밀도** — iPhone SE/mini 대응으로 폰트·여백을 한 단계 줄입니다.
- **가로 스크롤 0** — 4개 해상도 전부 확인.

```js
// DSL: 64×32 격자에만 그린다
D.px / D.rect / D.line / D.circ      (D.s=2 로 같은 부품을 2배로)

  ball(54,5,1); trail(54,5,4,DP.gold); sparks(54,5,DP.gold,7); crowdWave(); }
```

**총 43장** — 훈련 7 · 이벤트 7 · 경기 10 · 시즌 11 · 상태 8. 요구 1의 목록을 전부 덮습니다.

## 2. 유망주 등급 (요구 3) — "좋은 시작 ≠ 레전드"

```
평범한 유망주 75%  능력치 ×1.00
눈부신 유망주 23%  능력치 ×1.10
천재           2%  능력치 ×1.30
```

요구대로 시작 능력치를 주되, **세 축에서 대가를 받습니다.**

| | 잠재력 보정 | 성향 | 초기 스트레스 |
|---|---|---|---|
| 평범 | +8 | — | 20 |
| 눈부신 | +1 | 성실성 −7, 스타성 +10 | 32 |
| 천재 | **−12** | 성실성 **−22**, 인내 −12 | **50** |

- **잠재력 −12**: 일찍 완성된 선수는 천장이 가깝다 — 훈련 효율(`potRoom`)이 떨어진다
- **성실성 −22**: 재능을 믿는 선수는 훈련이 몸에 덜 붙는다
- **스트레스**: 기대의 무게. 성적이 기대(WAR 2.5)에 못 미치면 매달 `hype/5`씩 더 쌓이고, 스트레스는 **컨디션 → 슬럼프 → 감독 신뢰 → 강등** 체인을 탄다. v3.1에서 스트레스가 훈련 효율도 최대 30% 깎도록 연결했다.

### 측정이 불가능했던 지표를 분리했다

천재는 2%라 500커리어를 돌려도 **n=8~10**입니다. 그 표본으로 레전드 비율을 재니 같은 설정에서 **50%와 88%가 번갈아** 나왔습니다. 등급을 고정해 재는 전용 테스트를 따로 만들었습니다.

```js
testProspect(120)   // 등급마다 120회, 등급 고정
```

| 등급 | WAR 중앙 | 75% | 레전드(45+) | 실패(10−) |
|---|---|---|---|---|
| 평범한 유망주 | 19.7 | 38.1 | 18% | 41% |
| 눈부신 유망주 | 21.4 | 44.8 | 24% | 28% |
| **천재** | 35.3 | 48.9 | **36%** | **12%** |

보정 전에는 천재 레전드 **83%** / 실패 **3%** 였습니다. 지금은 천재가 유리하되(중앙 35 vs 20) 3분의 1만 레전드가 되고 8명 중 1명은 실패합니다 — 요구 3의 취지 그대로입니다.

## 3. 나이별 성장 효율 (요구 2)

```js
function ageEff(p){
  if(a<=21) return {gain:1.5,  fat:1.0,  fatAdd:5};   // 성장 빠름 / 피로 높음
  if(a<=23) return {gain:1.25, fat:1.0,  fatAdd:2};
  if(a<=29) return {gain:1.0,  fat:1.0,  fatAdd:0};
  if(a<=32) return {gain:0.75, fat:0.8,  fatAdd:0};
  return         {gain:0.5,  fat:0.55, fatAdd:0};     // 성장 느림 / 피로 낮음
}
```

훈련 화면에 `유망주 — 성장 ×1.5 · 피로 ×1 (+5)` 처럼 현재 보정을 표시합니다.

## 4. 표시값 = 실제값 (요구 13·14)

훈련 `sub`가 기본값(`컨택 +3.2`)을 보여주고 있었는데, 실제 적용값은 `TRAIN_SCALE × ageCurve × ageEff × 주간보정 × 컨디션 × 잠재력여유`를 거칩니다. **`trainPreview()`가 `doTraining()`과 같은 식을 쓰도록** 만들어 미리보기와 결과를 일치시켰습니다.

```js
/* doTraining() 과 같은 계수를 써야 "표시값 = 실제 변화" 가 성립한다.
   식이 바뀌면 이 함수도 같이 바꿔야 한다. */
function trainPreview(p,t,mult0,fatMul){ ... }
```

결과창의 `53 → 53 ▲ +0.1` 도 고쳤습니다. 화면은 정수로 찍으므로 **반올림했을 때 실제로 숫자가 바뀐 항목만** 보여줍니다(소수점 성장은 사라지지 않고 누적됩니다).

`↑↑`/`↓↓` 표현은 전부 제거했습니다 — 훈련 21종의 설명을 실측 수치로 바꾸고, 이벤트 55곳의 이중 화살표를 정리했습니다.

- **연봉 산정 확충** (요구 5) — 최근 3년 WAR 평균, 포지션 희소성(포수 ×1.18), 국가대표 경력, 부상 이력(누적 −3.5%/회, 큰 부상 −8%)을 추가.

## 6. 성능 — 화면마다 PNG를 인코딩하고 있었다

도트를 붙이자 자동 테스트가 **120커리어에 20분**이 걸렸습니다. `render()`가 매 화면 `dotURL()`을 부르고, 캐시 상한이 80이라 캐릭터 조합(포지션3 × 컨디션5 × 상태3 × 슬럼프2 × 팀10 = 900)에서 계속 밀려나 `toDataURL`이 다시 돌았습니다.

- 캐시 상한 80 → **400**
- 자동 테스트에 `G.noRender` — 엔진만 돌린다

### 남은 것

- **신인왕 0%** — 자격 창구를 데뷔 2년으로 넓혔지만 여전히 0에 가깝습니다. 데뷔 첫해는 시즌 중반 콜업이라 AI 신인에게 WAR로 밀립니다. 신인왕 판정을 출장 이닝/타석 기준으로 바꿔야 합니다.
